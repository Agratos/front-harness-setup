Target Design · harness-setup v3

알아서 개발하는 하네스로
무엇을 어떻게 바꿔야 하나

"사용하기 쉽게"와 "완벽하게 자율로"는 보통 상충하지만, 이 하네스에서는 해법이 같습니다. 오케스트레이터가 기억하고 지켜야 하는 것을 전부 코드로 옮기면 둘 다 해결됩니다.

01 — The answer

한 줄로 답하면

드라이버가 "다음에 뭘 해야 하는지" 를 말해주고, "그걸 했는지" 를 검사해야 합니다.

지금은 드라이버가 순서만 세고, 무엇을 할지는 md 를 읽어서 알아내고, 했는지는 아무도 안 봅니다.

이 한 문장이 두 요구를 동시에 만족시킵니다. 사용하기 쉬워지는 이유 — 오케스트레이터가 매 사이클 900줄짜리 md 뭉치를 읽고 규약을 암기할 필요가 없어집니다. 필요한 지시만 그때그때 받습니다. 자율성이 올라가는 이유 — 깜빡하거나 건너뛰면 드라이버가 전진을 거부합니다. "⛔ 하지 마세요" 를 md 에 적는 대신 코드가 막습니다.

지금 하네스에서 실패한 모든 사례(빈 병합, 스크린샷 미확인, Notion 미갱신, 폼 버그 통과)는 전부 "에이전트가 md 지시를 안 지킴" 이었습니다. 지키게 만드는 게 아니라, 안 지키면 진행이 안 되게 만드는 것이 설계의 전부입니다.

02 — Ergonomics

목표 사용 흐름 — 커맨드 3개

현재는 /copy-project → cd → yarn install → /start-project → /run-cycle ×N → /evaluate → /status 입니다. "알아서 개발" 의 사용자 경험은 이래야 합니다. 

$ /new ../my-app
  복사 → 설치 → git·Notion 연동 확인 → 심층 인터뷰 → plan.json 확정 → main 시드

$ /go
  status=done 까지 자율 진행. 페이즈마다 지시서 → 작업 → 검사 → 전진
  막히면 멈추고 이유를 말함 (영원히 돌지 않음)

$ /report
  현재 상태 · 수용기준 달성률 · 사이클별 소요 · 미해결 이슈

부분 실행이 필요할 때만 /go --steps=2, /go --phase(한 페이즈만) 를 씁니다.

/go 는 내부에서 harness next(지시서 받기) → 작업 → harness done(검사·전진) 을 반복합니다. 현재 /run-cycle 이 하던 일과 같지만, 규약이 md 가 아니라 지시서로 배달된다는 점이 다릅니다.

03 — The mechanism

핵심 장치: 작업 지시서

설계의 심장입니다. 드라이버가 현재 상태 · plan.json · 페이즈 계약을 조합해 이번 한 페이즈에 필요한 것만 출력합니다. 

$ node harness next

┌ CYCLE 3 · step 2/4 02-book-list · phase implement · rework 1/5
│
├ 해야 할 일
│    features/book-list 구현 — 아래 수용기준 3건을 만족시킬 것
│
├ 수용기준 (plan.json · 이 값이 곧 합격 조건)
│    AC-1  목록이 등록 순으로 정렬돼 표시된다
│    AC-2  상태 필터 변경 시 목록·통계가 즉시 반영된다
│    AC-3  0건일 때 빈 상태 안내가 보인다
│
├ 투입 에이전트 (기본값 — CEO 가 가감 가능)
│    ui · entity-modeler        감독: architect
│
├ 산출물 — 하나라도 없으면 전진 거부
│    ✗ step/02-book-list 브랜치 커밋 ≥ 1
│    ✗ src/ diff ≠ 0
│    ✓ harness/decisions/c3-design.md
│
├ 참고 — 이번 페이즈에만 필요한 문서
│    docs/fsd/features.md · .claude/agents/ui.md
│
└ 끝나면: node harness done

읽어야 할 것이 이 30줄로 줄어듭니다. 참고 문서도 이번 페이즈에 해당하는 것만 링크됩니다.

그리고 검사는 이렇게 거부합니다 — 이유와 다음 행동이 항상 붙습니다.

$ node harness done

✗ 전진 거부 — implement 산출물 미충족
   src/ diff 가 비어 있습니다 (step/02-book-list ↔ main)
   → 구현을 커밋한 뒤 다시 실행하세요.   재시도 1/3
      3회 초과 시 debate 로 보내 원인을 협의합니다

이 장치가 대체하는 것

지금바뀐 뒤
매 사이클 run-cycle.md 151줄 정독지시서 30줄
agent-roster.md 를 보고 subset 판단기본 subset 이 지시서에 인쇄됨 (CEO 가 가감)
⛔ 5개를 기억하고 지키기산출물 체크리스트가 코드로 검사됨
"이번엔 뭘 평가해야 하지" 를 매번 재구성AC 목록이 곧 채점표
실패하면 같은 자리 무한 반복재시도 한도 + 원인별 분기 + 항복 조건

04 — Changes

세 축의 변경

지시서가 성립하려면 아래 세 축이 함께 들어가야 합니다. 축 하나만 해도 개선은 되지만, 셋이 맞물릴 때 자율성이 생깁니다.

축 A

강제 — 코드가 검사한다

건너뛰기·가짜 통과를 물리적으로 불가능하게
phases.mjs
페이즈 계약
페이즈별 투입 에이전트 · 산출물 · 검사 조건 · 참고 문서를 한 파일에 선언합니다. 지금 run-cycle.md·agent-roster.md·AGENTS.md 표에 흩어진 규칙이 하나의 실행 가능한 정의로 모입니다. 지시서도 검사도 여기서 생성됩니다.
cycleId
신선도 스탬프
모든 산출물이 {cycleId, stepId, phaseSeq} 를 달고, 드라이버가 stale 을 거부합니다. cycleId = stepId#reworkCount 로 두면 같은 step 의 이전 재작업 회차 평가가 재사용되는 현재 구멍(F6)이 닫힙니다.
항상 전진
라이브락 제거
모든 실패는 카운터를 올리고 다른 페이즈로 보냅니다. 같은 자리에 머무르지 않습니다. 게이트 실패 → implement / 평가 stale → evaluate / N회 초과 → vote → 그래도 안 되면 blocked + 원인 리포트로 사람 호출. 자율의 반대말은 정지가 아니라 무한 루프입니다.
hooks
하네스 레벨 이중화
Stop 훅이 산출물 없이 턴이 끝나는 것을 막고, SessionStart 가 지시서를 자동 주입하고, PreToolUse 가 main 직접 커밋을 차단합니다. 드라이버를 안 부르고 끝내는 경로까지 덮습니다.
축 B

목적 — 무엇이 "완료"인가

점수가 아니라 요구사항으로 판정
plan.json
수용기준
인터뷰 결과가 step 별 acceptance[] 로 구조화되어 저장됩니다. 지금은 요구사항이 어디에도 기계가 읽을 형태로 남지 않습니다. 이게 있어야 "만든 게 요구를 충족했나" 를 물을 수 있습니다.
AC → 시나리오
자동 연결
각 acceptance 는 최소 1개의 E2E 단언과 짝지어져야 합니다. 짝이 없는 AC 가 있으면 verify 가 거부합니다. "테스트를 안 써도 통과" 와 "E2E 를 안 돌려도 통과" 가 동시에 닫힙니다.
체크리스트 판정
점수제 폐지
합격 조건을 "종합 90점"에서 "AC 전건 통과 + major 불만 0" 으로 바꿉니다. 90 은 조작 가능하지만 AC 5건 중 5건이 E2E 로 통과 는 조작이 어렵습니다. 점수·히스테리시스는 리포트용 지표로 남기고 게이트에서는 뺍니다.
verdict.json
주관 판정 구조화
스크린샷 육안 판정을 증거(캡처 파일 + 영역) 필수인 스키마로 받습니다. verdict 없으면 done-gate FAIL — "봤다고 치고 넘어가기"가 불가능해집니다. 객관(코드)과 주관(에이전트)을 분리해 각각 강제합니다.
축 C

조작성 — 부담을 덜어낸다

읽을 것과 기억할 것을 줄여 실패율을 낮춤
문서 다이어트
실행 규칙은 코드로, md 는 "왜"만. run-cycle.md 151줄은 지시서가 대체해 20줄로, notion-hub-layout.md 354줄은 notion-hub.mjs 코드 + 스펙 50줄로 줄입니다. 읽는 분량이 곧 실패율입니다.
Notion 코드화
LLM 은 "무엇을 쓸지" 만 정하고 "어떻게 쓸지"(relation 포맷·top-3 재작성·업로드)는 코드가 처리합니다. 3세대로 겹친 어댑터를 reporter 인터페이스 하나로 정리하면 Notion 없는 환경에서도 하네스가 돌아갑니다.
permissions 정리
.claude/settings.json 의 allowlist 로 yarn *·node scripts/*· git * 프롬프트를 없앱니다. 무인 실행 중 멈추는 원인 하나가 사라집니다.
골든 픽스처 CI
작은 요구사항 세트로 하네스 전체를 헤드리스 실행하고 결과를 단언합니다. 지금처럼 실제 프로젝트로 매번 손으로 N차 테스트하지 않아도 하네스를 고칠 때 회귀를 CI 가 잡습니다.

05 — Subtraction

더하는 것만큼 버리는 것

"사용하기 쉽게"의 절반은 삭제입니다. 아래는 이번 설계로 없어지는 것들입니다.

항목지금목표대체
사이클마다 읽는 md 분량≈ 900줄≈ 150줄작업 지시서 + 해당 페이즈 문서만
슬래시 커맨드6개3개/new · /go · /report
run-cycle.md 의 ⛔ 마크5개0개산출물 게이트가 코드로 검사
Notion 어댑터 세대3개1개reporter 인터페이스
합격 판정 기준종합 90점 + 히스테리시스AC 전건 통과점수는 리포트 지표로만
죽은 코드upsertDashboard 외삭제—

단, 버리면 안 되는 것 — 결정적 상태 기계 · 원자적 state · 멱등 재개 · git 안전장치 · self-test 문화. 이번 설계는 그 위에 얹는 것이지 갈아엎는 것이 아닙니다.

06 — Path

전환 경로 — 5단계

각 단계는 독립적으로 가치가 있고, 중간에 멈춰도 하네스가 지금보다 낫습니다. 순서는 안전망 → 계약 → 목적 → 조작성 → 정리입니다.

1약 1일

안전망 — 새는 곳부터 막기

  • gatesGreen 하드코딩 제거 30분
  • debate stepId 필터 + freshness 를 cycleId 단위로
  • 빈 병합 차단 (커밋 수 + src diff 검사)
  • verify/merge 실패 카운터 + 원인별 분기
얻는 것가짜 통과와 무한 루프가 사라집니다. 이후 단계의 전제 조건입니다.
22~3일

계약 — 페이즈에 입출력을 부여

  • harness/phases.mjs 신설 — 페이즈별 에이전트·산출물·검사·문서 선언
  • lib/artifact-gate.mjs — 산출물 존재·신선도 검사
  • loop.mjs 가 검사 통과 시에만 전진
  • eval-scenario 를 verify 에 배선 + CI 편입
얻는 것페이즈 스킵이 불가능해집니다. 규칙이 md 3곳에서 코드 1곳으로 모입니다.
33~4일

목적 — 요구사항으로 판정

  • harness/plan.json — 인터뷰 결과를 step + acceptance 로 구조화
  • AC ↔ E2E 단언 매핑 강제 (짝 없는 AC 는 verify 거부)
  • 합격 판정을 점수 → 체크리스트 소진으로 교체
  • verdict.json 스키마 + 증거 필수화
얻는 것"앱이 떴다" 가 아니라 "요구를 충족했다" 로 통과 기준이 바뀝니다. 여기가 자율성의 본체입니다.
42일

조작성 — 지시서와 커맨드 3개

  • harness next / harness done 구현 (phases.mjs + plan.json 조합)
  • .claude/settings.json + hooks 4종
  • 커맨드를 /new·/go·/report 로 통합
  • run-cycle.md 등 실행 규칙 md 축약
얻는 것매 사이클 읽는 분량이 1/6 로 줄고, 무인 실행이 프롬프트에 막히지 않습니다.
52~3일

정리 — 유지보수 비용 낮추기

  • Notion 을 reporter 인터페이스로 통합 + 죽은 코드 삭제
  • check-arch 4종 규칙 확장 ROI 최고
  • 골든 픽스처 CI + Windows matrix
  • report.mjs + metrics.ndjson + 예산 가드
얻는 것하네스를 고칠 때 회귀를 CI 가 잡고, 실패 패턴을 데이터로 봅니다.

07 — Honest limits

이 설계로도 해결되지 않는 것

남는 것은 전부 "판단"입니다

설계의 목표는 판단이 좋아지는 것이 아니라, 판단이 반드시 일어나게 하는 것입니다. 아래 셋은 코드로 검증할 수 없고, 앞으로도 LLM 몫입니다.

  • 구현 품질 — AC 를 만족하는 코드가 좋은 코드인지는 리뷰의 영역입니다.
  • 시각 판정 — 캡처를 본 것은 강제할 수 있어도, "잘 보인다"는 판단 자체는 못 합니다.
  • 요구사항 해석 — AC 를 잘못 뽑으면 전부 통과해도 원하는 물건이 안 나옵니다. 인터뷰 품질이 상한입니다.

그래서 /new 의 심층 인터뷰가 여전히 하네스에서 가장 중요한 단계이고, 지금처럼 생략 금지로 유지해야 합니다.

착수는 1단계부터를 권합니다. 하루면 끝나고, 여기까지만 해도 "평가가 통과했는데 실은 아무 일도 안 일어난" 사고가 사라집니다. 2·3단계가 실제 자율성을 만드는 구간이고, 4단계에서 체감 사용성이 바뀝니다.
