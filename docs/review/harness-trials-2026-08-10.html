04 — Conclusion

배운 것

하네스의 실패는 거의 전부 "md 에 적어뒀지만 아무도 검사하지 않는 것" 이었다.

새 기능을 넣어서 좋아진 게 아닙니다. 이미 존재하던 지시·도구를 검사 가능한 형태로 코드에 옮긴 것만으로 개입 5회 → 0회, 방어 실패 → 성공이 됐습니다. E2E 러너는 처음부터 있었고, 단지 아무도 부르지 않았습니다.

반영한 것

  • verify 가 E2E 를 직접 실행, 단언 실패 시 전진 차단
  • 실패를 설계결함 / 구현결함 / 검증결함으로 분류해 해당 페이즈로 되돌림 (사내 조직 가이드 규약 채택)
  • 재시도 3회 → 되돌림 → 3회 초과 시 blocked — 라이브락 제거
  • 평가 신선도를 사이클 단위로 (이전 재작업 회차 평가 재사용 차단)
  • 루브릭의 게이트 항목을 실측값으로 (하드코딩 만점 제거) · 빈 병합 차단
  • 스캐폴드가 제품 단계 진입 준비 완료 상태로 복사됨

남은 최우선 3가지

  • 페이즈 산출물 게이트 — 에이전트 페이즈(design·implement·evaluate·debate)는 아직 산출물 없이 전진한다
  • 루브릭 — 여전히 빈 스캐폴드에 100점을 준다. 육안 판정을 스키마로 받고 수용기준 차원을 추가해야 한다
  • plan.json — 요구사항→AC→E2E 추적성이 없어 "AC 4/4" 를 사람이 세고 있다
