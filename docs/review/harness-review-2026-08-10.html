03 — Root cause

발견 대부분은 한 줄로 수렴합니다

"작업이 실제로 일어났는가"를 코드가 검증하지 않습니다.

페이즈 8개 중 코드가 실제로 무언가를 강제하는 것은 verify 와 merge 둘뿐입니다. 나머지는 로그 한 줄을 남기고 무조건 전진합니다.

코드가 강제하는 것

  • 페이즈 시퀀싱 · 멱등 재개
  • 결정적 게이트 4종
  • 평가 임계치 · 히스테리시스
  • 재작업 5회 → 투표 분기
  • 브랜치 보호 · merge 게이트
  • dev 서버 teardown

md 준수에만 의존하는 것

  • 구현이 실제로 있었는가
  • 토론·평가가 실제로 있었는가
  • 스크린샷을 실제로 봤는가 (B3)
  • E2E 시나리오를 실제로 돌렸는가
  • Notion 허브 갱신 (354줄 사양)
  • 에이전트 subset 선정 · 투표 내용

오른쪽 목록에서 아래 두 개(선정·투표)는 판단이므로 md 가 맞습니다. 나머지 넷은 판단이 아니라 산출물의 존재 여부이므로 코드로 옮길 수 있습니다. 이 이동이 이번 개선의 전부라고 봐도 됩니다.

04 — Findings

발견 사항 14건

F1P0

에이전트 페이즈는 무조건 전진합니다

증상loop.mjs:267-280 에서 decompose·design·implement·evaluate·debate·vote 는 산출물 유무를 확인하지 않고 전진합니다. 

# 코드 0줄, 결정 0건, 토론 0회로 한 step "완주"
node scripts/loop.mjs   × 7회  →  status 전진 완료

merge 의 done-gate 가 막아줄 것 같지만, 빈 스캐폴드는 게이트 4종을 통과하고 루브릭도 90+ 를 줍니다(F3). 실제로 차단되지 않습니다.

해결페이즈 산출물 게이트 — 전진 전에 산출물 존재 + 신선도(stepId·phaseSeq 스탬프)를 검증하고, 없으면 전진 거부 + exit 2.

페이즈요구 산출물 (신선도 스탬프 포함)
decomposedecisions/<id>.md + plan.json 의 해당 step 수용기준
designdecisions/<id>-arch.md
implementstep 브랜치 커밋 ≥1 AND src/ diff ≠ 0
evaluateevaluations/<id>.json + <id>.verdict.json
debatedecisions/<id>.md 의 해당 라운드 섹션
F2P0

빈 병합이 코드로 막히지 않습니다

증상run-cycle.md:118 이 "구현 커밋 안 하면 빈 병합" 을 ⛔ 로 경고합니다(실사고 기록). 그런데 git-flow.mjs:231-263 의 cmdMergeStep 은 커밋 수도 diff 도 보지 않습니다.

해결merge 직전 git rev-list --count main..step/<nn>-<slug> > 0 과 src/ 경로 diff 비어있지 않음을 강제. 규모: 소

F3P0

루브릭이 품질을 측정하지 못합니다 (확정 버그 포함)

증상rubric.mjs 의 16개 항목이 전부 "앱이 떴는가" 수준입니다. 빈 스캐폴드가 90~100점을 받습니다.

확정 버그eval-playwright.mjs:360,365,369 가 gatesGreen: true 를 하드코딩해서 넘깁니다. 

// eval-playwright.mjs:360
observations = await playwrightObservations(pw, port, shotPath, {
  gatesGreen: true,   // ← 실측 아님. 항상 통과
  expectedName: expectedAppName(repoRoot),
});

q.gates-green 은 weight 40 · major 항목이라 종합 8점이 게이트 실제 상태와 무관하게 항상 지급됩니다. layoutStable 도 같은 상수입니다.

구조진짜 품질 신호는 B3(에이전트가 스크린샷을 눈으로 보는 것)인데, 그 판정이 점수로 들어가는 코드 경로가 없습니다. 에이전트가 <id>.json 을 손으로 고쳐야 하고, 그건 곧 주관 점수 자유 기입 = 가짜 통과 벡터입니다.

해결3단계로 나눠 처리합니다.

  • gatesGreen 을 done-gate --deterministic-only --json 실측값으로 교체 30분
  • 육안 판정을 <id>.verdict.json 스키마로 받고 eval-merge-verdict.mjs 가 루브릭과 합성. verdict 없으면 done-gate FAIL → 육안 평가가 코드로 강제됨
  • 루브릭에 "수용기준 충족" 차원 추가(가중치 0.3+) — F5 의 plan.json 과 1:1 매칭
F4P0

E2E 러너가 게이트에 배선되어 있지 않습니다

증상eval-scenario.mjs 는 스스로 "최대 갭"이라 기록한 항목인데, 실행 경로가 없습니다.

  • done-gate.mjs 에서 호출 안 함
  • loop.mjs 의 verify 페이즈에서 호출 안 함
  • CI self-test 목록에 eval-scenario.selftest.mjs 누락 (ci.yml:38-49)
  • 스펙 파일 없으면 passed: true 로 skip (eval-scenario.mjs:163)

md 3곳에 "⛔ 무조건"이라 써 있지만 실행은 100% 오케스트레이터 자율입니다.

해결verify 페이즈에서 실행 + 스펙 부재 자체를 결함으로 승격 (step 당 최소 N개 단언, 면제는 decisions 에 명시 기록) + CI 편입.

F5P1

사양 → 스텝 → 수용기준 → 평가 추적성이 0

증상planSteps 가 ["01-login","02-dashboard"] 문자열 배열뿐입니다. deep-interview 로 뽑은 요구사항이 어디에도 구조화되어 저장되지 않고, decompose 산출물은 md 라서 아무 코드도 읽지 않습니다. "만든 게 요구사항을 충족하나"를 판정할 근거가 시스템에 없습니다.

해결harness/plan.json 도입

{ "steps": [{
  "id": "01-login", "goal": "...",
  "acceptance": ["이메일 형식 오류 시 제출 차단", "성공 시 /home 이동"],
  "scenarios": ["fill → click → assert inputEmpty"],

F6P0

실패 시 라이브락 — 탈출구가 없습니다

증상loop.mjs:260-266 — verify/merge 실패 시 전진하지 않고 committed=false 로 두어 같은 페이즈를 영원히 재실행합니다. 실패 카운터도 에스컬레이션도 없습니다.

가중여기에 결함 둘이 겹칩니다.

  • resolveDebateOutcome(loop.mjs:117-132)이 stepId 를 안 봅니다. 이전 step 의 평가로 debate 가 pass → merge → done-gate 가 stale 거부 → merge 무한 반복.
  • freshness 가 step 단위입니다(done-gate.mjs:299). 같은 step 의 rework 1회차 평가(100점)가 3회차 merge 에서 그대로 통과합니다. phaseSeq 비교가 없습니다.

해결resolveDebateOutcome 에 stepId 필터 / freshness 를 phaseSeq ≥ 이번 사이클 evaluate 시작 seq 로 강화 / verifyFailCount·mergeFailCount 추가 → N회 초과 시 implement 회귀, 재초과 시 vote 또는 blocked + report.md 원인 리포트.

F7P1

협의체 모델이 실행 가능한지 미검증

증상pm.md:4 가 tools: …, Task 로 선언하고 문서 전체가 "PM 이 K=3 으로 서브에이전트를 호출한다"를 전제합니다. 그런데 이 환경의 스폰 도구명은 Agent 이고(Task 는 구 명칭), 서브에이전트가 다시 서브에이전트를 스폰하는 것은 일반적으로 지원되지 않습니다.

즉 PM 코디네이터 릴레이는 문서상 구조일 뿐이고, 실제로는 메인 오케스트레이터가 다 하고 있을 가능성이 높습니다. K=3 · 3라운드 반박 · PM 경유 릴레이가 전부 그 위에 얹혀 있습니다.

해결실측 확인 후 둘 중 하나 — (a) 오케스트레이터 = PM 으로 모델 재정의(문서 정합), 또는 (b) scripts/pm.mjs 가 페이즈별로 에이전트를 순차 호출하도록 코드화.
