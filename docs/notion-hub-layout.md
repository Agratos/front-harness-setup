## 1. 페이지 구조

```
🏢 Harness <프로젝트명> Inc.
└─ 💡 상단 콜아웃 (프로젝트 설명 + 상태줄)
   📋 하네스 계획   → top-3 불릿 + 인라인 DB
   🔄 진행 상황     → top-3 불릿 + 인라인 DB(🔄 Cycles)
   🚨 이슈          → top-3 불릿 + 인라인 DB(🚨 이슈 트래커)
   🚀 배포 관리     → top-3 불릿 + 인라인 DB
   🤖 에이전트 설명 → 안내문 + 인라인 DB(👥 Team Roster)
   📝 회의록        → 안내문 + 인라인 DB(📝 Meeting Notes)
   📚 참고 자료     → (현재 비어 있음)
```

- 각 섹션 = `## `(h2) 헤더 + 인라인 DB. 섹션 사이는 `---`.
- **각 데이터 섹션(계획·진행 상황·이슈·배포)은 DB 블록 바로 위에 "top-3 불릿"** 을 둠 — 그 섹션에서 지금 중요한 상위 3개(진행 중·열림 우선)를 한눈에 보여주고, 전체는 아래 인라인 DB로 확인(§1.1).
- DB 간 **relation**으로 서로 연결(§3)되어 클릭으로 오갈 수 있음.

### 1.1 섹션 상단 top-3 불릿 (요약 미리보기)

각 데이터 섹션의 인라인 DB **바로 위**에, 그 섹션의 **중요도 상위 3개**를 순수 텍스트 불릿으로 보여준다(전체 목록은 아래 DB). 한눈에 현재 상태를 파악하기 위한 미리보기.

| 섹션 | top-3 선정 기준(중요도 순) | 불릿 형식 |
| --- | --- | --- |
| 📋 하네스 계획 | 진행 중 → 계획 수립 → 최신 요청일시 | `• <요청> — <상태>` |
| 🔄 진행 상황 | 진행 중 → 번호(최신 사이클) 내림차순 | `• <사이클> — <상태> · 평가 <score>` |
| 🚨 이슈 | 열림(논의 중·논의 전) → 심각도(P0>P1>P2) | `• <이슈> — <상태>` |
| 🚀 배포 관리 | 배포일 내림차순(최신) | `• <버전> (<환경>) — <상태>` |

**자동 갱신 (`run-cycle.md` §Notion 허브 갱신):** 오케스트레이터가 어떤 섹션 DB에 행을 쓸 때마다, 그 섹션 top-3를 다시 뽑아 **불릿 블록을 통째로 재작성**한다(커넥터, 의도된 자동화).
- 커넥터는 DB 행을 **조회하지 못하므로**, 행 목록은 `harness/notion-state.json` **로컬 레지스트리**로 관리하고 Notion 을 되읽지 않는다.
- ⚠️ 불릿 재작성의 `new_str` 에는 **순수 텍스트만** 넣고 `<database>` 태그는 **절대 포함하지 않는다**(중복 DB 양산 방지 — §8). 헤더(`## …`)를 old_str로 잡아 그 아래에 불릿만 추가하면 DB 블록은 건드리지 않는다.

**현재 라이브 예시값 (각 섹션 3건):**
- 📋 계획: 차량 검수 이력 조회(진행 중) · 검수자 대시보드 위젯(계획 수립) · PDF 리포트(대기)
- 🔄 진행 상황: 사이클 5(진행 중) · 사이클 4(완료 · 평가 8) · 사이클 3(완료 · 평가 8.5)
- 🚨 이슈: 상태·날짜 동시 필터 누락(논의 중) · 빈 목록 깜빡임(논의 전) · 직렬화 오류(해결)
- 🚀 배포: v0.2.1(staging) · v0.2.0(staging) · v0.1.0(dev) — 모두 성공

## 2. 상단 콜아웃 (💡, blue_bg)

```
**프로젝트 설명** — <한 줄 설명>           ← 콜아웃 rich_text (1줄, 설명만)
**<상태이모지> <상태>**　·　**사이클 N / M**　·　**최근 배포 <버전> (<환경>)**　·　**열린 이슈 <K>건**   ← 콜아웃의 자식 paragraph (상태줄, 딱 1개)
```
- **구조(중요)**: 콜아웃 `rich_text` = **프로젝트 설명 1줄만**. 상태줄은 콜아웃의 **자식 paragraph 블록 1개**. ⚠️ 상태줄을 rich_text 에 넣으면 자식 상태줄과 **중복**된다(A1 버그). 초기화/갱신 모두 **자식 paragraph 를 update**(없으면 1개 생성, 추가 자식은 삭제).
- **초기화(§1b)**: 설명=새 프로젝트 한 줄, 상태줄 자식=중립(예: `🟡 준비　·　사이클 0 / N　·　열린 이슈 0건`). 옛 프로젝트 상태줄 자식은 반드시 교체(잔존 금지).
- **사이클마다 갱신(run-cycle)**: decompose 진입 시 `🔵 진행 중 · 사이클 N/M`, merge/배포 시 `최근 배포 <ver>`·`열린 이슈 K`, 완주 시 `🟢 완료 · 사이클 M/M` 으로 **상태줄 자식만** 다시 쓴다(설명 rich_text 는 유지). ⚠️ 과거 테스트에서 상태줄이 `사이클 0/N` 으로 stale 했던 건 이 갱신 누락(A1-②).
- 구분자: 전각 가운뎃점 `　·　`(앞뒤 전각공백 U+3000).
- 예시값(완주 시): `🟢 완료 · 사이클 3 / 3 · 최근 배포 v0.1.0 (dev) · 열린 이슈 0건`

## 3. DB 관계 맵 — DB는 서로 연결됨 (핵심)

```
📋 하네스 계획  ↔  🔄 진행 상황(사이클)  ↔  🚨 이슈 트래커
                      ↕
                  🚀 배포 관리
```

| 관계 | 의미 |
| --- | --- |
| 계획.`진행 상황` ↔ 진행 상황.`계획` | 계획 ↔ 그 계획의 사이클들 |
| 진행 상황.`이슈` ↔ 이슈.`진행 상황` | 사이클 ↔ 그 사이클의 이슈들 |
| 진행 상황.`이슈 수` (rollup count) | 사이클의 이슈 개수 |
| 진행 상황.`배포` ↔ 배포 관리.`진행 상황` | 사이클 ↔ 그 사이클이 낸 배포 (비면 미배포) |

- 모든 relation 은 **dual(양방향)** — 한쪽에서 연결하면 반대쪽에 역방향 컬럼 자동 생성.
- ⚠️ **relation 은 컬럼만으로 자동 연결 안 됨.** 행 생성/수정 시 **값(연결 대상 페이지 URL 배열)** 을 채워야 연결됨. 예: 사이클 생성 시 `계획` 지정, 이슈 생성 시 `진행 상황`(현재 사이클) 지정, 배포 시 `진행 상황` 지정. 값 형식: `"[\"https://app.notion.com/p/<id>\"]"`.
- ⚠️ 에이전트는 진행 상황(`에이전트`)·이슈(`발의`)에만 둠 — 계획엔 별도 에이전트 없음(relation으로 사이클 통해 확인).

## 4. 데이터베이스 스키마 + 표시 컬럼

행 생성: `notion-create-pages`, `parent = { type:"data_source_id", data_source_id:<ds id> }`.
표 표시 컬럼은 `displayProperties` 기준(나머지는 숨김 — 행 열어서 확인).

> 아래 DB/ds ID는 **예시 허브 값** — 실제로는 **허브를 fetch 해 얻은 현재 ds ID**를 쓴다(프로젝트마다 다름). 컬럼명·타입·옵션은 프로젝트가 같은 템플릿이면 동일.
>
> 📌 **모든 date 컬럼은 시간 포함(datetime)** 으로 기록한다 — 값 쓸 때 `"date:<컬럼>:is_datetime"`=`1` + ISO 일시(`…T17:30:00`). (§8 참조)

### 📋 하네스 계획
- DB `9f705d7cde4782a98df90191ee06977a` · ds `fe205d7c-de47-8313-9e99-07b3945773c2`

**한 행 = PO/사용자가 낸 개발 요청 1건.** 하네스가 이 계획을 여러 사이클로 분해해 진행하며, 그 사이클들은 `진행 상황` relation 으로 묶인다(역방향 자동). 즉 *"무엇을 만들기로 했나"* 의 최상위 단위.

| 속성 | 타입 | 값/옵션 | 언제·누가 기록 |
| --- | --- | --- | --- |
| 요청 | title | 계획 제목 (예: `차량 검수 이력 조회 화면 추가`) | 요청 등록 시 |
| 계획 요약 | text | 범위·접근(FSD 경로 등) 한두 줄 | 등록/계획 수립 시 |
| 상태 | select | 대기 ⚪ / 계획 수립 🟡 / 진행 중 🔵 / 완료 🟢 | 진행에 따라 |
| 요청일시 | date | 시간 포함 (`date:요청일시:start` + `is_datetime`=1) | 등록(또는 진행 중 전환) 시 |
| 종료일시 | date | 시간 포함 | 완료 시 |
| 진행 상황 | relation → 진행 상황 | 이 계획의 사이클들 (클릭형 칩, 역방향 자동) | 사이클 생성 시 자동 |

**상태 전이:** `대기` → `계획 수립` → `진행 중` → `완료`.
**표시 컬럼:** 요청 · 상태 · 요청일시 · 종료일시
> 계획은 보통 사람이 등록한다. 사이클 연결(`진행 상황`)은 사이클을 만들 때 그쪽에서 `계획`을 지정하면 자동으로 채워진다(직접 입력 불필요).

### 🔄 진행 상황 (DB 제목: 🔄 Cycles) — ⭐ 핵심 허브 DB
- DB `ac505d7cde4783cc8b1e811cc8f16ce2` · ds `bf105d7c-de47-8315-af91-876400d3e8eb`

**한 행 = 하네스 루프의 한 사이클(step).** `decompose → design → implement → verify → evaluate → debate → merge` 한 바퀴가 한 사이클이며(필요 시 `vote` 분기), 이 DB가 *"지금 무엇이 어디까지 진행됐나"* 의 단일 뷰입니다. 위로 **계획**, 아래로 **이슈·배포** 를 relation 으로 잇는 **중앙 허브 DB**(§3) — 다른 DB는 모두 이 사이클을 거쳐 연결됩니다.

| 속성 | 타입 | 값/옵션 | 언제·누가 기록 |
| --- | --- | --- | --- |
| 사이클 | title | 예: `사이클 5 — 날짜 범위 필터` | 사이클 시작(`decompose`) 시 |
| 계획 | relation → 하네스 계획 | 이 사이클이 속한 계획 1건 (클릭 시 계획으로) | 시작 시 (계획 URL 배열로 연결) |
| 상태 | select | 예정 ⚪ / 진행 중 🔵 / 완료 🟢 / 보류 🟡 | 페이즈 전이마다 갱신 |
| 에이전트 | multi_select | 이번 사이클 투입 agent — planner·architect·ui·entity-modeler·qa·customer·quality·ux·ceo·pm 중 (JSON 배열 문자열) | CEO 가 페이즈 subset 선정 시 |
| 이슈 | relation → 이슈 트래커 | 이 사이클에서 제기된 이슈들 (클릭형 칩) | 이슈 생성 시 (양방향 자동) |
| 이슈 수 | rollup (count) | `이슈` relation 개수 자동 집계 | (자동) |
| 배포 | relation → 배포 관리 | 이 사이클이 낸 배포 (비면 미배포) | `merge` 후 배포 시 |
| 평가 | number | done-gate 종합 score — **≥90 병합 진입, ≥88 유지(래치)** | `evaluate` 페이즈 |
| 한 일 | text | 사이클 산출 요약 | 완료 시 |
| 번호 | auto_increment_id | 자동 증가 (정렬 키) **readOnly** | (자동) |
| 날짜 | date | 시간 포함 (`date:날짜:start` + `is_datetime`=1) | 시작/완료 시 |

**상태 전이:** `예정`(decompose 전) → `진행 중`(작업 중) → `완료`(merge 성공). 외부 차단이면 `보류`.
- 재작업(rework)은 상태를 바꾸지 않고 `진행 중` 유지. `debate`가 `rework` 판정 → `implement` 로 되돌리며 카운트 +1, **5회 초과 시 vote 분기**(§6 회의·투표 메커니즘과 동일).
- `평가`(score)와 done-gate 관계: 90 이상이어야 병합 진입, 한번 통과하면 88까지 유지(미세 변동 플래핑 방지), 88 미만 또는 major 불만 발생 시 탈락.

**표시 컬럼(Default view):** 사이클 · 계획 · 상태 · **평가** · 에이전트 · 이슈 · 배포
> ⚠️ `평가`(score)는 done-gate 핵심값이라 **기본 뷰에 반드시 표시**한다(과거 기본 뷰에서 누락돼 표에 안 보이던 버그 → A2 보강). 새 허브 셋업 시 `notion-update-view configure: 'SHOW "사이클","계획","상태","평가","에이전트","이슈","배포"'`.
**보조 뷰 `한눈에`:** 사이클 · 상태 · 에이전트 · 평가 · 날짜 (번호 내림차순 정렬)

**행 작성 예시** (`notion-create-pages`, parent = ds `bf10…`):
```json
{
  "사이클": "사이클 5 — 날짜 범위 필터",
  "계획": "[\"https://app.notion.com/p/<계획 페이지 id>\"]",
  "상태": "진행 중",
  "에이전트": "[\"planner\",\"architect\",\"ui\"]",
  "평가": 92,
  "한 일": "date-range 위젯 + validator 연결",
  "date:날짜:start": "2026-06-15T17:30:00",
  "date:날짜:is_datetime": 1

```
> `이슈`·`배포` relation 은 사이클 행에서 직접 채우지 않아도 됩니다 — **이슈/배포 행을 만들 때 그쪽에서 `진행 상황`을 이 사이클로 지정하면 양방향 자동 연결**되고, `이슈 수` rollup 도 자동 갱신됩니다.

**상태 전이 = 회의 진행과 1:1 대응:**
- `논의 전 🔴` — 행만 생성, 아직 회의 미개시.
- `논의 중 🟡` — 본문에 `### 회의 1` 이상 진행 중(주장 + 이유 + 투표 누적).

⚠️ **`발의` ≠ 회의 참석자.** `발의`에는 이슈를 **연 에이전트**만 넣습니다. 실제 토론 참여자와 표 분포는 이슈 본문 회의(§6)에 적습니다.

**표시 컬럼:** 이슈 · 진행 상황 · 발의 · 상태 · 결론 (이슈 1건당 한 줄 — WRAP CELLS로 다중 칩은 세로로 쌓임, §5)
**회의 기록 본문 구조는 §6 참조.**

**행 작성 예시** (`notion-create-pages`, parent = ds `5a00…`):
```json
{
  "이슈": "날짜 역전 입력 검증 누락",
  "진행 상황": "[\"https://app.notion.com/p/<사이클 페이지 id>\"]",
  "발의": "[\"qa\",\"customer\"]",
```

## 5. 표시 규칙 — 가로 스크롤 방지

- DB 뷰는 **핵심 컬럼만 표시(SHOW)** → 가로 스크롤 억제. 긴 텍스트·부가 relation은 숨기고 행 클릭으로 상세 확인.
- 도구: `notion-update-view` `configure: "SHOW \"col1\", \"col2\", …"`, `"WRAP CELLS true"`, `"SORT BY \"col\" DESC"`.
- **WRAP CELLS true** 켜둠 → relation 칩이 여러 개여도 셀이 세로로 늘어나(가로 X) 한 개씩 쌓임.
- relation 컬럼 = **클릭형 페이지 칩** (클릭 시 대상으로 이동). "아이콘만" 모드는 없음 — 더 좁히려면 UI에서 컬럼 폭 드래그.
- ⚠️ **컬럼 폭은 UI 전용**(API 불가) — 한번 맞추면 행 작성으로는 안 바뀜. 단 `update-view`로 컬럼 구성을 바꾸면 폭이 초기화될 수 있으니 구성 확정 후 호출 최소화.

## 6. 이슈 회의 기록 규칙 (이슈 페이지 본문)

이슈 페이지 **본문(body)** 에 `## 💬 에이전트 회의` 아래 **`### 회의 1`, `### 회의 2` …** 라운드별로:

- 각 회의에서 에이전트가 **주장 + 이유(왜)** 를 적고 → **🗳 투표**(집계).
- 이견이면 **다음 회의**로 재논의·재투표. **5라운드 초과(합의 미달) 시 CEO 캐스팅보트**로 확정 (run-cycle.md debate/vote 규칙).
- 최종 결정은 이슈 DB의 **`결론` 필드** + `상태` 갱신(논의 전→논의 중→해결).
- 댓글이 아니라 **페이지 본문**에 작성(`notion-update-page` `replace_content`/`insert_content`). (Notion 댓글은 API로 삭제 불가라 본문 사용.)

**본문 구조 예시** (이슈 페이지 body):

```markdown
## 💬 에이전트 회의

### 회의 1
- **qa**: endDate < startDate 입력이 검증 없이 서버로 간다. (이유: e2e에서 역전 값이 그대로 통과)
- **architect**: 클라이언트 validator 한 곳에서 막자. (이유: 서버 왕복 비용·UX)
- **ui**: 제출 버튼 disable 로 충분. (이유: 별도 에러문구는 과함)
- 🗳 투표 — validator 추가 2 (qa, architect) / 버튼 disable 1 (ui) → **과반 미달, 재논의**

### 회의 2
- **ui**: validator + 인라인 에러문구 수용. (이유: disable 만으론 사용자에게 이유 전달이 안 됨)
- **qa**: 동의. **architect**: 동의.
- 🗳 투표 — validator + 인라인 에러 3 / 0 → **만장일치 → 결론 확정**
```

→ 위 결론을 이슈 DB `결론` 필드에 `shared/lib/validator에 dateRange 추가 + 폼 인라인 에러 노출` 로 기재하고 `상태`를 `해결`로 변경.
- **합의되면 짧게:** 1라운드에서 만장일치면 회의 1 하나로 종결(억지 라운드 금지). 이견이 있을 때만 회의 2, 3…으로 이어가며 각 라운드에 **주장 + 이유 + 투표 집계**를 남깁니다.

## 8. MCP 도구 메모 (현재 세션 기준)

| 작업 | 가능 | 방법 |
| --- | --- | --- |
| 본문(제목/콜아웃) 수정 | ✅ | `notion-update-page` (`update_properties`/`update_content`/`insert_content`/`replace_content`) |
| DB 행 생성 | ✅ | `notion-create-pages` (parent = `data_source_id`) |
| DB 스키마 변경 | ✅ | `notion-update-data-source` `statements:`(SQL DDL: ADD/DROP/RENAME/ALTER COLUMN, RELATION, ROLLUP) |
| 뷰 설정(표시 컬럼·정렬·줄바꿈) | ✅ | `notion-update-view` `configure:`(SHOW/SORT/WRAP CELLS) |
| 데이터소스 휴지통/복원 | ✅ | `notion-update-data-source` `in_trash:true/false` (단 페이지 블록 복원은 UI가 확실) |
| 댓글 추가 | ✅ | `notion-create-comment` (단 삭제 불가 → 회의는 본문 사용) |
| DB 행 **조회/삭제** | ❌ | query·trash 도구 미노출 → Notion UI |
| 인라인 DB 블록 **위치 이동**, 컬럼 폭 | ❌ | UI 전용 (커넥터 시도 시 중복 DB 양산 이력 — 금지) |

값 전달 주의:
- multi_select: JSON 배열 **문자열** — `"[\"ui\",\"qa\"]"`
- relation: 페이지 URL JSON 배열 문자열 — `"[\"https://app.notion.com/p/<id>\"]"`
- date: **모든 날짜 값은 시간 포함**으로 기록 — `"date:<컬럼>:start"` = ISO 일시(예 `2026-06-15T17:30:00`) + `"date:<컬럼>:is_datetime"` = `1` (항상). Notion은 "시간 포함"이 값 단위라 속성 토글이 없음 → **쓸 때마다 `is_datetime`=1**.
- select: 옵션명 그대로(공백 포함) — `"진행 중"`
- rollup 함수 토큰: `count`(count_all 아님), count_values, sum, average …
